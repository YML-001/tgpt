## 执行摘要（Executive Summary）

**一句话**：为全校师生提供统一的团学新闻投稿入口。学生走五级审核，学院教师和职能部门老师各走一条四级审核，全程留痕、按时限督办，采用结果计入统计并支持升华网发布。

**概述**：平台面向全校学生和教职工（统一身份认证登录，无“通讯员”等单独开通的投稿角色），支持新闻、视频、照片、线索四类稿件。学生稿件依次经过指导老师、学院副书记、一审、二审、校团委终审；教师稿件依次经过学院副书记、一审、二审、校团委终审；职能部门老师稿件依次经过副职领导、学生一审、学生二审、校团委终审。副书记是学工系统的固定角色，按投稿人所在学院自动路由，平台不维护名单。副职领导按职能部门配置，同一部门可有多人，稿件进入该部门全体在任副职领导的待办，任一人审核即可。所有审核角色使用同一套“我的待办”（待办 / 已办 / 催办抄送 / 批量审批 / 办理），并提供与职责匹配的稿件查询。管理员负责终审、统计驾驶舱、学院排行榜、档案库、升华网发布素材、线索跟进、超时台账、人员名单、业务参数、意见模板、敏感词库和操作日志。角色权限是固定规则，不提供在线配置页。

**要点速览**：

- 目标用户：全校师生（投稿人，含学生、教师、职能部门老师）、指导老师、学院副书记、副职领导、一审员、二审员、校团委管理员。
- 解决的问题：稿件收集分散、审核不留痕、时效无人督办、学院采用无法统计。
- 核心指标：审核节点按时处理率（审核及时率）。
- 终端：PC 管理后台 + 移动端 H5（全部角色的高频操作）。

## 1. 问题陈述（Problem Statement）

### 1.1 问题

团学新闻素材目前通过微信群、邮箱等渠道层层转交，存在四个问题：

1. 投稿入口分散，稿件版本混乱，图片被压缩，原图难找。
2. 审核意见不留痕，退回原因和修改过程无法追溯。
3. 各审核环节没有时限，积压稿件无人督办。
4. 学院投稿量、采用量没有统一口径，排行榜和年度考核缺少依据。

### 1.2 现状

学生稿件通常先找老师把关，再交学院，再交校团委宣传部逐级修改；教师稿件路径不固定。终审采用后由人工整理正文和图片发布到升华网，再人工统计各学院采用数。

### 1.3 影响

- **对投稿人**：不知道稿件卡在哪一环、为什么被退回。
- **对审核人员**：待审稿件分散在多个渠道，容易遗漏或超时。
- **对校团委**：无法按学院、类型、时间统计投稿与采用，也无法证明审核及时与否。

### 1.4 为什么现在做

学校要求团学宣传工作纳入学院考核，需要可追溯的审核记录和可信的采用统计。学院副书记作为学工系统固定角色加入学生和教师稿件的审核链，按学院自动路由，平台不维护副书记名单。职能部门的工作稿件不经过学院副书记，改由该部门在任副职领导先审，再进入校团委学生一审、学生二审。

## 2. 目标与非目标（Goals & Objectives）

### 2.1 业务目标

1. **统一入口**：全校师生通过统一身份认证即可投稿，四类稿件全部线上提交。
2. **全程留痕**：每个节点的审核人、结果、意见、时间、IP 写入不可删除的操作日志和稿件流转记录。
3. **时效可控**：每个审核节点按工作日计时，超时自动记入台账并催办。
4. **统计可信**：终审结果自动生成“计入 / 不计入采用”的归档属性，驱动学院统计与排行榜。
5. **发布提效**：已采用的新闻稿可一键获取清洗后的正文和原图素材包。

### 2.2 用户目标

1. 投稿人能随时看到稿件处于哪个节点，并能按意见修改重提；重提后回到该身份的第一站。
2. 学生能在本院已配置的指导老师中指定人选，职能部门老师能在本部门在任副职领导中指定负责领导；名单没有的人按工号回显，不能手填姓名。教师不选人。
3. 审核人员在一个待办列表里处理全部稿件，超时稿件优先；剩余时限在办理页看，列表只保留时效筛选。
4. 指导老师、副书记、副职领导能回查自己审核过的稿件；一审员、二审员能浏览全校档案；管理员用稿件档案库。
5. 管理员能配置时限（含副职领导审核时限）、名单、意见模板和敏感词；角色权限为固定规则，不提供在线配置页。

### 2.3 非目标

- 不做通讯员等需要单独开通的投稿账号体系。
- 不在平台内维护副书记名单或副书记分配规则（取自学工系统）。
- 不在平台内存储视频文件（使用永久云盘链接）。
- 不自动发布到升华网（人工发布后在平台标记“已发布”）。
- 不做稿件内容的在线协同编辑。

## 4. 用户故事与需求（User Stories & Requirements）

优先级：P0 为上线必需，P1 为上线应有，P2 为可后续迭代。规模：S / M / L。

### 史诗 A：投稿（P0）

#### 故事 A1：选择身份并投稿

作为（As a）全校师生，我希望（I want）登录后选择学生、教师或职能部门老师身份并提交四类稿件之一，以便（So that）稿件自动进入正确的审核流程。

**验收标准（Acceptance Criteria）**

- 投稿人姓名、所属学院取自统一身份认证，表单中只读。电脑端和手机端的投稿、修改重提使用同一套身份切换。
- 选择“学生”时必须指定指导老师。下拉默认只列出投稿人本学院、且已在指导老师名单中的人员（陈雨桐 / 计算机学院默认可见王海峰、李晓琳）。可在框内按姓名筛选这些人。名单之外或不在本学院的人员，在同一控件输入工号，按人员库回显姓名、单位、职务后点选或回车选定；未知工号显示空结果，不能手填姓名。
- 选择“教师”时不出现人选控件，并提示提交后先由本院副书记审核，再进入校团委一审。不为副书记做人员选择。
- 选择“职能部门老师”时不显示指导老师。投稿人选择所属部门，并指定负责领导。负责领导下拉默认只列出该部门已配置且在任的副职领导；其他人员用工号回显后选定，未知工号不能手填姓名。
- 提交成功页按身份显示下一节点：学生显示“待指导老师审核”，教师显示“待副书记审核”，职能部门老师显示“待副职领导审核”，进度条后续节点写“学生一审”“学生二审”。
- 优先级 P0，规模 L；对应 `pc/correspondent/submit-*.html`、`submit-success.html`，`mobile/correspondent/submit-*.html`。

#### 故事 A2：新闻与视频附件、新闻选填项

作为（As a）投稿人，我希望（I want）新闻稿的配图和活动简介可以不填，并能为新闻和视频上传多个附件，以便（So that）没有配图的稿件也能投，相关材料随稿件一起归档。

**验收标准（Acceptance Criteria）**

- 新闻“活动简介”“新闻配图”无必填标记，不做必填校验；只填标题、撰稿人、拍摄时间、不少于 50 字的正文即可提交。
- 新闻、视频各有“附件”区：可多选，单个不超过 50MB，格式为 doc / docx / pdf / xls / xlsx / ppt / pptx / zip / rar / txt / jpg / jpeg / png；列表显示文件名、大小、类型图标，可逐个删除，并实时显示已上传数量。
- 退回修改页使用与新闻投稿相同的字段规则。
- 优先级 P0，规模 M。

#### 故事 A3：草稿、自动保存与敏感词检测

作为（As a）投稿人，我希望（I want）内容自动保存，并在提交前知道是否包含敏感词，以便（So that）不会丢稿，也不会因违规内容被退回。

**验收标准（Acceptance Criteria）**

- 编辑中每 30 秒自动保存草稿，也可手动“保存草稿”。
- 提交时检测：命中高危词则拦截，提示词语并要求修改；命中低危词则提示，用户可选择仍然提交；白名单词组不触发。
- 必填项未填时标红并滚动定位到首个错误字段。
- 优先级 P0，规模 M。

#### 故事 A4：修改重提与版本

作为（As a）被退回稿件的投稿人，我希望（I want）对照历次退回意见修改并重新提交，以便（So that）稿件重新进入审核，同时保留历史版本。

**验收标准（Acceptance Criteria）**

- 修改页顶部展示历次退回意见；“本次修改说明”必填。
- 重新提交生成新版本号，旧版本与意见永久保留，不可覆盖。
- 重新提交后从该身份的首个审核节点重新流转：学生回到指导老师，教师回到副书记，职能部门老师回到副职领导。修改重提页沿用同一套指导老师 / 负责领导选择控件。
- 新闻稿可查看“版本对比”，并排标注新增与删除内容。
- 优先级 P0，规模 M；对应 `resubmit.html`、`version-history.html`。

### 史诗 B：审核流转（P0）

#### 故事 B1：学生稿件五级审核

作为（As a）学生投稿人，我希望（I want）稿件依次经过指导老师、学院副书记、一审、二审、校团委终审，以便（So that）稿件质量和导向层层把关。

**验收标准（Acceptance Criteria）**

- 状态依次为：待指导老师审核 → 待副书记审核 → 待一审 → 待二审 → 待三审 → 已终审采用 / 已终审不采用。
- 指导老师办理页的通过按钮为“通过，提交副书记审核”；副书记的为“通过，报送一审”。
- 节点流程图为：开始、指导老师审核、副书记审核、一审、二审、三审终审、采用归档。
- 优先级 P0，规模 L。

#### 故事 B2：教师稿件四级审核

作为（As a）教师投稿人，我希望（I want）稿件不经过指导老师，先由本院副书记审核，以便（So that）流程更短但仍有学院把关。

**验收标准（Acceptance Criteria）**

- 教师稿件提交后状态为“待副书记审核”。
- 节点流程图为：开始、副书记审核、一审、二审、三审终审、采用归档。
- 任何页面不得出现“教师投稿直接进入一审”的表述。
- 教师身份不提供副书记人选控件。
- 优先级 P0，规模 S。

#### 故事 B2a：职能部门老师稿件四级审核

作为（As a）职能部门老师，我希望（I want）稿件不经过指导老师和副书记，先由所属部门的副职领导审核，以便（So that）部门工作稿件由部门把关后再进入校团委。

**验收标准（Acceptance Criteria）**

- 流程为：副职领导审核 → 学生一审 → 学生二审 → 校团委终审。学生一审、学生二审仍由现有一审员、二审员办理，不新增账号类型，也不改一审员、二审员菜单名称。
- 提交后状态为“待副职领导审核”。任一节点退回都回到投稿人。
- 路由：稿件进入投稿人所属部门在副职领导名单中全体在任人员的待办，同部门多人时任一人完成即可，其他人的待办自动移除。
- 进度条、流程图、成功页在这条流程上使用“学生一审”“学生二审”。
- 优先级 P0，规模 L；对应 `pc/vice/`、`mobile/vice/`、`pc/admin/vice-manage.html`。

#### 故事 B3：副书记自动路由

作为（As a）学院副书记，我希望（I want）系统自动把本院稿件送到我的待办，以便（So that）管理员不需要维护副书记名单或做分配。

**验收标准（Acceptance Criteria）**

- 副书记由学工系统提供，按“投稿人所在学院 → 学院副书记”路由。
- 平台不提供副书记的新增、编辑、导入或分配界面。
- 人员名单页和导航页的角色说明中注明“副书记取自学工系统，无需配置”。
- 副书记待办和稿件查询只包含本院稿件。
- 优先级 P0，规模 M。

#### 故事 B4：退回与终审

作为（As a）任一审核人员，我希望（I want）退回时必须填写意见并可插入模板，以便（So that）投稿人知道如何修改。

**验收标准（Acceptance Criteria）**

- 指导老师、副书记、副职领导、一审、二审都可以“通过”（意见选填）或“退回”（意见必填，最多 500 字，可插入本环节的意见模板）。
- 任一节点退回后，稿件状态为“已退回”并通知投稿人；投稿人重提后从首节点重新流转。
- 终审只能二选一：“采用”的统计归档为“计入采用”；“不采用”须填写终审意见，统计归档为“不计入采用”。
- 优先级 P0，规模 M。

#### 故事 B5：时限与超时督办

作为（As a）管理员，我希望（I want）每个节点按工作日计时并自动督办超时稿件，以便（So that）稿件不积压。

**验收标准（Acceptance Criteria）**

- 默认时限：指导老师、副书记、副职领导、一审、二审、三审各 3 个工作日，在“业务参数”中按节点分别配置，节假日不计入。待办列表不单独显示剩余时限列，办理页仍显示剩余时间，时效筛选保留。
- 剩余时限低于“超时预警提前量”（默认 1 个工作日）时标记“即将超时”，超时标记“已超时”并排在待办最前。
- 超时记入“超时台账”，系统自动催办并在“催办/抄送”中留痕；管理员可人工催办。
- 优先级 P0，规模 M。

### 史诗 C：统一待办（P0）

#### 故事 C1：待办、办理、已办、催办抄送、批量审批

作为（As a）审核人员，我希望（I want）用同一套“我的待办”处理所有稿件，以便（So that）换角色也不需要重新学习。

**验收标准（Acceptance Criteria）**

- **待办**：列为序号、流程名称（“类型审核：《标题》”+编号）、当前节点、发起人（学院·身份）、发起时间、到达时间、操作（列表不单独显示剩余时限列，批量审批列表同样不显示）；可按流程名称、发起人、时效（已超时 / 即将超时 / 正常）筛选；超时行标红；默认按超时优先、到达时间升序排序；剩余时限在办理页显示。
- **办理页**：页签为表单信息、流程图、审批记录、操作日志。学生稿和教师稿的基础信息为编号、类型、投稿人和身份、所属学院、指导老师（教师稿显示无需指定）、副书记（注明学工系统）、流程发起时间、到达本节点时间。职能部门老师稿件改为所属部门、副职领导（列出该部门在任人员）、审核路由说明，不出现指导老师和副书记。流程图按身份绘制：职能部门老师为副职领导审核、学生一审、学生二审、三审终审。另含该类型的全部稿件字段、敏感词检测结果、剩余时限。
- **已办**：列为流程名称、节点、发起人、流程状态（已通过 / 已退回，终审为已采用 / 不采用）、意见、处理时间、时效（及时 / 超时，附用时）；可筛选、可导出。
- **催办/抄送**：两个页签，分别列出催办消息和抄送消息，各自可筛选。
- **批量审批**：按全部、新闻、视频、照片、线索分类；批量通过需二次确认，不填意见；批量不通过必须填写意见。
- 处理完成后返回待办，该稿件从待办中移除，并给出前往已办查看的入口。
- 优先级 P0，规模 L；对应 `_build/workflow.py`、`_build/review.py`。

### 史诗 D：稿件查询（P1）

#### 故事 D1：指导老师、副书记、副职领导查询本人审核过的稿件

作为（As a）指导老师、副书记或副职领导，我希望（I want）在“稿件查询”菜单查看我审核过的稿件及其后续去向，以便（So that）跟踪稿件最终是否被采用。

**验收标准（Acceptance Criteria）**

- 筛选：关键词（标题 / 编号 / 投稿人，输入即查）、学院或部门、类型、流转状态、本人审核结果、投稿身份、投稿日期起止；提供“立即查询”“重置”；无结果时显示空状态；可导出当前结果。
- 点击行按类型打开对应稿件档案（新闻 / 视频 / 照片 / 线索），菜单保持“稿件查询”高亮。

#### 故事 D2：一审员、二审员浏览全校档案

- 优先级 P1，规模 S。

### 史诗 E：管理员（P0 / P1）

#### 故事 E1：人员名单（一审员、二审员、指导老师）

**验收标准（Acceptance Criteria）**

- 人员库中没有的工号可以“手动填写”后保存；工号已在名单中时给出提示，但不拦截保存（正式系统建议改为拦截，见待决问题）。
- 任期为“开始日期 至 结束日期”两个日期框，均必填，结束日期不得早于开始日期；表格显示为“YYYY-MM-DD 至 YYYY-MM-DD”。

#### 故事 E1a：副职领导名单

作为（As a）管理员，我希望（I want）按部门维护副职领导，以便（So that）职能部门老师的稿件能送到本部门的副职领导。

**验收标准（Acceptance Criteria）**

- 支持与一审、二审相同的 CSV 导入、导出和学年换届。
- 页面以只读说明写出路由：稿件进入投稿人所属部门全体在任副职领导的待办，任一人审核即可。

#### 故事 E2：一审员、二审员导入导出

作为（As a）管理员，我希望（I want）用 CSV 批量导入导出审核人员，以便（So that）每学期换人时不必逐个录入。

**验收标准（Acceptance Criteria）**

- 导入：提供模板下载（列为姓名、工号、所在学院、职务、任期开始、任期结束，UTF-8）；仅接受 .csv；表头缺列时提示具体缺少哪些列。
- 导入预览逐行显示：可导入、缺少某些字段、工号重复（已在名单中）、工号重复（文件内重复）、任期日期有误；只写入有效行，并提示“新增 N 人，跳过 M 行”。
- 优先级 P1，规模 M。

#### 故事 E3：学年换届

作为（As a）管理员，我希望（I want）一次性完成续任和离任，以便（So that）换届结果准确且可追溯。

- 确认前二次提示续任和离任人数。确认后：续任人员保持在任、启用，任期改为新任期；离任人员标记“已离任”、停用，任期结束日改为新任期开始的前一天，开始日期保留。

- 优先级 P1，规模 M。

#### 故事 E4：终审、档案、发布、线索、统计

作为（As a）管理员，我希望（I want）在一个后台完成终审、统计、发布和线索跟进，以便（So that）校团委的工作闭环。

## 5. 成功指标（Success Metrics）

### 5.1 北极星指标

- **指标**：审核及时率。
- **口径**：时限内处理的节点次数 ÷ 全部节点处理次数。
- **原型演示值**：94.8%，为演示数据，不能作为基线。
- **目标**：上线一学期后 ≥ 95%。
- **理由**：直接反映流程是否顺畅、督办是否有效。

### 5.2 次要指标

| 指标 | 目标 | 时间 |
|------|------|------|
| 线上投稿占全部团学稿件的比例 | ≥ 90% | 上线后一学期 |
| 覆盖学院比例（至少有 1 篇投稿） | 100%（全部学院） | 上线后一学期 |
| 退回稿件附有意见的比例 | 100% | 持续 |
| 平均审核总时长（提交到终审） | ≤ 8 个工作日 | 上线后一学期 |
| 超时节点占比 | ≤ 5% | 上线后一学期 |
| 已采用新闻从终审到标记“已发布”的中位时长 | ≤ 2 个工作日 | 上线后一学期 |
| 移动端完成的审核操作占比 | ≥ 40% | 上线后一学期 |

### 5.3 埋点事件（建议）

- `submission_submit`：提交或重提，带类型、身份、版本。
- `review_action`：通过、退回、采用、不采用，带节点、用时、是否超时。
- `query_filter`：稿件查询或档案库发起筛选。
- `export`：任意导出，带范围。
- `publish_mark`：标记已发布。

## 7. 技术考量（Technical Considerations）

### 7.1 总体架构

建议采用前后端分离：PC 管理后台与移动端 H5 共用一套后端 API。原型是由 Python 生成器 `_build/` 输出的静态 HTML，加上共享脚本 `assets/app.js` 和演示数据 `assets/mock-data.js`；它只作为界面与交互参考，不作为代码基础。

### 7.2 外部集成

| 系统 | 用途 | 要求 |
|------|------|------|
| 统一身份认证 | 登录、姓名、学院、身份（学生 / 教职工）、学号或工号 | 投稿身份由投稿人在表单中选择，但需与认证信息校验一致（见待决问题） |
| 学工系统 | 学院副书记（学院 → 人员），可能还有辅导员信息 | 定时同步加变更推送；副书记变动后，新到达的稿件路由到新人员，已在途稿件的处理方式见待决问题 |
| 人员库 | 新增审核人员、指导老师时按工号回显姓名、学院、职务 | 原型使用内置的小型人员库 |
| 消息渠道 | 站内消息，可选移动门户推送 | 第二阶段 |
| 升华网（博达站群） | 人工发布 | 不对接接口，仅提供素材 |

### 7.3 数据模型（核心实体）

- **稿件**：编号（TG + 年月日 + 序号）、类型、标题、投稿人、投稿身份、学院、所属部门（职能部门老师）、指导老师（学生）、负责领导（职能部门老师）、当前状态、当前节点、当前版本、统计归档属性、发布状态、线索处置状态（仅线索）、创建时间、提交时间。
- **稿件版本**：版本号、类型字段快照、修改说明、提交时间。
- **附件 / 图片**：所属版本、种类（配图、照片、封面、附件）、原始文件名、大小、存储地址、单张备注（照片）。
- **审核任务**：稿件、节点、处理人、到达时间、截止时间（工作日）、处理时间、结果、意见、是否超时。
- **催办与抄送记录**、**消息**、**操作日志**。
- **人员名单**：一审员、二审员、指导老师、副职领导。字段为工号、姓名、学院或所属部门、职务、任期开始、任期结束、状态（在任 / 已离任，或启用 / 停用）、累计审核数或指导稿件数。副职领导按部门配置，同一部门可多人。
- **配置**：节点时限、预警提前量、节假日、统计周期、类型开关、上传限制、意见模板、敏感词库（高危、低危、白名单、变体）、检测设置。

### 7.4 状态机与路由

**流转状态**：草稿、待指导老师审核、待副书记审核、待副职领导审核、待一审、待二审、待三审、已退回、已终审采用、已终审不采用、已发布。职能部门老师流程中，一审、二审的展示文案为“学生一审”“学生二审”，状态值仍可沿用待一审、待二审。

| 当前状态 | 动作（执行人） | 下一状态 |
|----------|----------------|----------|
| 草稿 | 提交（学生） | 待指导老师审核 |
| 草稿 | 提交（教师） | 待副书记审核 |
| 草稿 | 提交（职能部门老师） | 待副职领导审核 |
| 待指导老师审核 | 通过（指导老师） | 待副书记审核 |
| 待副书记审核 | 通过（副书记） | 待一审 |
| 待副职领导审核 | 通过（副职领导） | 待一审（展示为学生一审） |
| 待一审 | 通过（一审员） | 待二审 |
| 待二审 | 通过（二审员） | 待三审 |
| 待三审 | 采用（管理员） | 已终审采用，计入采用 |
| 待三审 | 不采用（管理员，意见必填） | 已终审不采用，不计入采用 |
| 任一“待…审核”节点（终审除外） | 退回（意见必填） | 已退回 |
| 已退回 | 修改重提（投稿人） | 新版本；学生回到待指导老师审核，教师回到待副书记审核，职能部门老师回到待副职领导审核 |
| 已终审采用（仅新闻） | 标记已发布（管理员） | 已发布 |

**路由规则**：

- 指导老师：学生在表单中指定。下拉默认本学院已配置名单，工号回显可以指定其他单位人员。
- 副书记：投稿人所在学院在学工系统中的副书记。教师和学生稿件使用，不提供人选控件。
- 负责领导：职能部门老师在表单中指定，下拉默认所属部门已配置的在任副职领导，工号回显可以指定其他人员。
- 副职领导待办：进入投稿人所属部门全体在任副职领导，任一人完成即可。
- 一审、二审：原型只说明“分配给本人”，具体分配规则见待决问题。职能部门老师稿件的展示名称为学生一审、学生二审。
- 终审：校团委管理员。

**其他状态体系**：

- 线索处置状态：无需处理、待跟进、已跟进、已转为正式新闻。
- 统计归档属性：计入采用、不计入采用。
- 时效标识：正常、即将超时、已超时；已办结果标为及时或超时。

以上三套与流转状态分开存储。

### 7.6 接口建议

接口仅作示意，命名由后端确定：

- 稿件：`GET /api/submissions`（按角色数据范围返回，支持关键词、学院、类型、状态、身份、日期、本人审核结果、分页、排序）、`POST /api/submissions`、`POST /api/submissions/{id}/resubmit`、`GET /api/submissions/{id}`（含版本、附件、流转、日志）。
- 审核任务：`GET /api/tasks/todo`、`GET /api/tasks/done`、`POST /api/tasks/{id}/pass`、`POST /api/tasks/{id}/reject`、`POST /api/tasks/batch`。
- 稿件查询：`GET /api/reviewed?role=teacher|deputy|vice`，返回本人已处理、非在途的稿件；vice 再按所属部门限制。
- 名单：`GET/POST/PUT /api/rosters/{kind}`，kind 含 reviewer1、reviewer2、teacher、vice。`POST /api/rosters/{kind}/import`（先预校验再提交）、`GET /api/rosters/{kind}/export`、`POST /api/rosters/{kind}/term-change`（新任期、续任 ID 列表）。
- 人员回显：`GET /api/people?no=`，供名单新增和投稿选人。投稿选人另需按学院返回已配置指导老师、按部门返回在任副职领导。
- 配置：不提供权限配置接口。`/api/config/params`、`/api/config/templates`、`/api/config/sensitive`。权限在服务端按 4.3 写死。
- 发布：`GET /api/submissions/{id}/publish-text`、`GET /api/submissions/{id}/publish-zip`、`POST /api/submissions/{id}/published`。

### 7.7 安全与审计

- 授权：在服务端执行“功能权限 + 数据范围”双重校验；直接访问他院稿件返回无权页。
- 操作日志：记录新建、提交、编辑（修改前后）、重提、各级审核、退回、终审、标记发布、参数变更、名单变更（含导入、换届）、数据导出、下载。日志字段为操作时间、操作人账号与姓名、身份、操作行为、对象稿件编号、IP、详情或修改前后；只读，可导出。
- 涉密提示：投稿页提示“涉密信息请勿上网”。

### 7.8 性能与规模

按全校约 20 个学院、年稿件量数千篇、图片附件为 TB 级估算（原型统计中本学年 1024 篇为演示值）。列表一律使用服务端分页，前端默认每页 15 条；图片附件走对象存储，原图存档，另生成预览缩略图。

### 8.3 主要流程

1. 投稿人新建投稿，选择身份，填写表单并提交，进入提交成功页，在我的投稿中高亮新稿件。
2. 审核人员在待办中打开办理页，选择通过（意见选填）或退回（意见必填），返回待办，该稿件被移除，可去已办查看记录。
3. 投稿人收到退回消息，打开稿件档案查看意见，修改重提，生成新版本，稿件从首节点重新流转。
4. 管理员终审采用（新闻）后，复制正文或导出素材包，人工发布，再标记已发布。
5. 管理员在一审员或二审员名单中做学年换届：设置新任期、勾选续任、二次确认，表格即时更新，状态筛选同步生效。

### 8.4 稿件详情（四类）

**公共区块**

- 审核进度条（学生 7 步，教师 6 步，含采用归档）。
- 页签：稿件内容、审核流程（节点流程图）、审批记录（各节点审核人、时间、意见）、操作日志；新闻另有修改历史。
- 基础信息：稿件编号、类型、投稿人、投稿身份、所属学院、指导老师（教师稿件显示“无需指定”）、副书记（注明学工系统）、投稿时间、当前状态、是否计入采用。

**按类型的内容区**

- **新闻**：标题、撰稿人、拍摄时间、学院、正文字数、活动简介（未填时显示“未填写”）、正文与插图、全部配图（未上传时显示提示）、附件列表（可下载）。
- **视频**：视频标题、拍摄 / 撰稿人、时长、用途、用途补充说明、链接有效期、永久云盘链接（可复制）、提取码、封面图、视频简介、附件列表。
- **照片**：照片主题、拍摄人、拍摄时间、照片数量、涉及重要领导、场景简述、照片网格（文件名、大小、单张备注）。
- **线索**：线索标题、线索类型、线索来源、事件时间地点、是否接受采访、可采访时间段、联系人、联系方式、处置状态、线索内容。

**适用页面**

- 投稿人稿件档案。
- 指导老师、副书记、一审、二审的办理页与已办详情。
- 指导老师、副书记、一审、二审稿件查询中的档案页。
- 管理员终审页与档案库详情。
- 移动端详情与审核页。

办理页右侧显示剩余时限与敏感词结果；非新闻类型的检测范围按类型说明。

### 8.5 交互约定

- **列表**：筛选条件区配合“立即查询”“重置”；关键词支持输入即查；可排序列点击表头切换升序或降序；分页可切换每页条数；无数据时显示空状态。
- **二次确认**：提交、终审、停用、换届、参数保存、标记发布、删除草稿等操作需要确认。
- **处理结果反馈**：审核或提交后返回列表，显示结果条，并给出“查看已办”等链接。
- **按钮行为**：所有按钮都有明确行为；导出均实际生成文件。

### 8.6 无障碍与适配

- PC 主要适配 1440 宽度，最小 1200；移动端适配 390 宽度。
- 表单控件有可读标签，错误提示紧邻字段，颜色之外另有文字标识（如“已超时”）。

## 10. 风险与应对（Risks & Mitigation）

| 风险 | 影响 | 应对 |
|------|------|------|
| 学工系统副书记数据不全或延迟 | 学生或教师稿件无人审核 | 同步失败时告警管理员；无副书记的学院稿件如何兜底见待决问题 |
| 某部门没有在任副职领导 | 职能部门老师稿件无人接收 | 换届和停用时提示补人；未配置部门不出现在投稿人的部门下拉中 |
| 副书记人员变动时稿件在途 | 在途稿件卡住 | 制定在途任务转交规则（见待决问题） |
| 审核员换届频繁 | 名单与权限不同步 | 使用学年换届与导入功能；停用即时收回权限 |
| 敏感词误判 | 正常稿件被拦截 | 白名单、语义 / 精准模式切换、试测功能 |
| 原图与附件占用存储 | 成本上升 | 对象存储分层；视频走云盘链接 |
| 云盘链接失效 | 视频素材丢失 | 审核时提示核对链接；后续可做定期检测 |
| 原型演示行为被误当成需求 | 实现偏差 | 以附录 14.2 为准 |

## 11. 依赖与假设（Dependencies & Assumptions）

**依赖**

- 统一身份认证能提供学院与身份类型。
- 学工系统能提供“学院 → 副书记”数据。
- 学校的对象存储或文件服务。
- 节假日数据由管理员维护，也可另行对接学校校历。

**假设**

- 每个学院在同一时间只有一名负责投稿审核的副书记。若实际有多名，路由规则见待决问题，平台仍不维护副书记名单。
- 同一部门可以有多名在任副职领导，稿件同时进入每人待办，任一人完成即可。
- 一审员、二审员、指导老师、副职领导均有工号可在人员库中查询；查不到的工号在名单维护里允许手填，在投稿选人里不允许手填姓名。
- 终审只由校团委管理员执行。学生一审、学生二审不新增账号。
- 退回后一律从该身份的首节点重新流转，不支持只退回到上一节点。

## 12. 待决问题（Open Questions）

**已决（按当前原型执行，不再作为开放问题）**

- 不提供“角色权限配置”页，权限按 4.3 固定实现。
- 副书记不建名单，取自学工系统，教师和学生稿件都不提供副书记人选。
- 三条审核流程、选人规则、副职领导按部门路由、待办列表不显示剩余时限列，均以第 4 章和第 7.4 节为准。
- 管理员不单独做“本人终审过的稿件”菜单，由稿件档案库和已办覆盖。

**仍待确认**

1. 一审、二审的任务分配方式：公共池抢单、轮询，还是指定分配？原型仅显示“分配给本人”。职能部门老师稿件进入学生一审后，沿用同一套分配规则。
2. 原型中投稿人自行选择学生、教师或职能部门老师。正式系统是否必须与统一身份认证的人员类别一致，教职工兼读学生时如何处理？
3. 学院有多名副书记时按什么规则路由？副书记变动时，已经在途的稿件如何转交？平台仍然不维护副书记名单。
4. 人员名单里工号重复时，是否拦截保存？原型只提示，仍允许保存。
5. 指导老师名单的批量导入，是否改成与一审、二审、副职领导相同的预校验？原型里指导老师导入只提示成功。
6. 移动端的落地形态是 H5、企业微信，还是学校移动门户？站内消息之外的推送渠道是什么？
7. 一审员按学期轮换，换届操作是否也叫“学年换届”，默认新任期如何设定？

### 14.2 原型限制（不是需求）

- 数据为 `_build/data.py` 与 `assets/mock-data.js` 中的固定演示数据，各角色之间不实时同步。
- 审核结果通过网址参数（如 done、new、msg）传递给下一页，刷新后不保留。
- 同一类型的稿件共用一份示例正文（新闻用一篇示范稿，视频、照片、线索各一份）。列表点击不同的同类稿件时，详情页的编号和标题会变，但内容相同；正式系统必须展示各稿件自身的数据。
- 查询、筛选、排序、分页、导出都在浏览器内对页面数据执行。每页 15 条是原型的默认值，正式系统应在服务端分页，每页条数可选。
- 工号回显使用内置的小型人员库；名单导入、学年换届、附件上传只修改当前页面，不保存。
- 指导老师名单的“批量导入”仅提示成功。
- 敏感词检测在前端执行，词库为演示词表。
- 统一身份认证、学工系统、消息推送、升华网均未对接。
- ZIP 素材包由浏览器端打包，图片来自示例图源。

### 14.3 术语

- **副书记**：投稿人所在学院的副书记，学工系统固定角色，不提供人选控件。
- **副职领导**：按职能部门配置的审核人。职能部门老师投稿时指定负责领导，稿件进入该部门全体在任副职领导的待办。
- **负责领导**：职能部门老师在投稿表单中指定的人选，下拉默认本部门已配置的副职领导。
- **统一待办**：所有审核角色共用的待办、已办、催办抄送、批量审批、办理模块。
- **统计归档属性**：终审后生成的“计入 / 不计入采用”。
- **升华网**：学校新闻门户（博达站群）。
- **学年换届**：批量续任和离任审核人员的操作。
